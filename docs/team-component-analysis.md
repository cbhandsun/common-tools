# Remote component reconstruction

The image worker can run the local two-pass component workflow: analyze the current page, match verified offline component assets, then pass the real strategy and asset indexes into native reconstruction. Component matching does not guarantee that a page has a suitable template or that visual quality passes.

Enable the worker with `deploy/compose.team-component-assets.yaml` in addition to the existing deployment overlays. Set `COMMON_TOOLS_COMPONENT_ASSET_STORE` to the host directory containing `asset-registry.json` and `assets/sha256`. The overlay mounts only those paths, read-only, and sets `COMMON_TOOLS_IMAGE_COMPONENT_ASSET_ROOT=/app/component-assets`. Rebuild the image worker using the updated Dockerfile before enabling it.

The registry loader selects assets with promoted, passed self-fidelity evidence and verifies hashes and portable paths. The registry is limited to 4 MiB, 100 assets and 60 MiB of selected files. Invalid configured stores fail startup; an unconfigured worker preserves its existing single-pass behavior. The workflow performs no online component search or automatic download.

The internal inventory retains verified paths and matching features; only public evidence is path-free. Unmatched layers keep the existing native detectors. Offline raster-preservation and template-only recommendations cannot suppress those detectors; component asset indexes remain available to the existing native group admission logic. After reconstruction, output provenance retains compact asset references rather than embedding learning summaries or duplicate template geometry.

Each page is analyzed independently. Reports must refer to the current image or semantic shape layer, and selected files must belong to the verified inventory. Source hashes are checked before and after analysis. Per-page `source.componentAnalysis` records the source hash, analysis layer count, asset match count and bounded component-family evidence for detected, matched, strategy-ready and still-missing layers. Zero matches remain zero; they must not be presented as proof of native reconstruction parity. File byte counts stay internal to avoid introducing unrelated large numeric values into deck IR.

The component asset golden gates can require specific native component families with `requiredComponentFamilies` in the coverage or regression manifests. Use this for reusable corpus expectations such as `matrix-table`, `process-flow`, `relationship-network` and `timeline-roadmap`; a candidate must show at least one applied native component in every required family, not only satisfy an aggregate family-count threshold.

Image-to-PPT component recall can be gated separately from final native application with `minImageComponentDetectedFamilyTypes`, `minImageComponentMatchedFamilyTypes`, `minImageComponentStrategyFamilyTypes` and `maxImageComponentMissingFamilyTypes`. These gates intentionally read `source.componentAnalysis` image-analysis evidence rather than `componentFamilyAppliedCounts`, so a corpus can prove the pre-rebuild component recall path without treating detection as native reconstruction.

Coverage and real-PPTX quality matrices also emit `componentFamilyBacklog`, which ranks unresolved family work by funnel stage: asset match, strategy routing, native application, first native coverage or expansion. They also emit `componentFamilyActionPlan`, a ranked queue with the owner surface, blocking metric, deficit count, acceptance gate and evidence metrics for each unresolved family. Use `maxCriticalComponentFamilyBacklogItems` when a reusable corpus or regression run must fail on critical family gaps instead of leaving them as report-only follow-up items; use the action plan to choose the next asset-promotion, strategy-routing or native-application change.

The reusable image-to-editable recall corpus contract lives in `skills/pd-hifi-slideclone/examples/image-to-editable-component-recall-corpus.manifest.json` and is planned with `npm run slideclone:image-to-editable-component-recall-corpus`. Refresh reusable local corpus artifacts with `npm run slideclone:image-to-editable-component-recall-fixtures` before running strict acceptance against an image-to-editable runtime that emits measured `source.componentAnalysis`. The fixture materializer creates approved local source PNGs, runs the local image-to-editable job, stores generated `deck.json` and PPTX artifacts, preserves analyzer-produced `source.componentAnalysis` evidence, fails when expected families are absent, and writes per-case component-candidate reports when the manifest asks for them. Each case declares the source image/PDF, expected component families, generated `deck.json`, generated PPTX, optional component-candidate report, and the accepted `image-to-editable-component-recall-report` plus `image-to-editable-component-recall-gate` profiles. The default corpus covers cycle/loop, hierarchy, fishbone, funnel, layered architecture, matrix/table, overlap, process, pyramid, relationship/network, specialty chart and timeline families. Use `--require-artifacts` on the corpus script only for acceptance runs where those generated artifacts are expected to exist.

Component asset promotion should pass through `npm run slideclone:component-self-fidelity-batch` followed by `npm run slideclone:component-asset-admission-gate`. The admission gate reads the self-fidelity batch report, verifies the original PPTX hash, replay PPTX, self-fidelity report, known component family/motif evidence, native editable object evidence and region comparison evidence, then emits admitted/rejected asset summaries. Keep `--fail-on-reject` enabled for reusable asset-library promotion so bitmap-only or evidence-light assets cannot enter the reusable component pool.

`test/team-component-analysis.test.js`, `test/team-component-catalog.test.js` and `test/team-component-wiring.test.js` are automatically discovered by the unit CI suite. They cover real offline search/matcher compatibility, index forwarding, report/source boundaries and the multi-megabyte source metadata regression. Existing visual fidelity and native component gates remain unchanged.
