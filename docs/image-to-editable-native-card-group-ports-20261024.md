# 完整卡片与连接器的分组端口验证

本轮从当前真实原图输出继续处理整卡拖动缺口。生产源码、正式 PPTX、源图、阈值及已批准近似范围未修改，整页仍为 11 条已接纳关系、严格区域 9/12。两个共享图的 44 个原生连接器和 88 个端点引用继续以此前绑定产物为准，本轮未新增 Office 跟随通过结论。

## 已查明的边界

`source-scene-connector-group-scope.js` 会拒绝使原生连接器和其端点进入不同 Office 绘制容器的分组。这个保护保留了单独节点轮廓的连接引用，同时使相接业务卡片的填充、轮廓、绘制覆盖层无法自动作为完整卡片保留分组。上次五次拖动选中了外观层而非实际锚定轮廓，符合这个结构缺口；不能把 XML 有端点引用当作整卡操作已通过。

当前 `ConnectorAttachmentWriter` 能绑定真实形状，也有仅供其私有构造的 positioned-text 组委托到真实文字子形状的逻辑。普通卡片组没有对应的端口委托实现。直接删除容器兼容保护或只给卡片增加分组 ID，尚不能证明 Office 行为正确。

[诊断目录](../.codex-temp/native-card-group-ports-20261023-v1/preparation.json)包含一张卡片组、一个外部节点和一条真实双端连接器。卡片组包含原生底框、徽标和文字。`child-bound.pptx` 由当前实际 .NET writer 生成，连接器引用组内真实底框；`group-bound.pptx` 仅在诊断副本里将该起点引用改为组 ID，保留原连接 site 3。后者有明确的写后 XML 修改，不能充当生产 writer 已支持卡片组端口的证据。

## Office 通道的实际阻塞

本轮通过 computer-use 的 `@oai/sky` 成功发现 PowerPoint。两次 `launch_app` 都报告超时；随后同一通道重新列举返回了唯一 PowerPoint 窗口，说明启动超时本身不是进程未启动的证据。对这个真实返回窗口的状态读取显示 Windows 安全中心正在请求 Node.js JavaScript Runtime 的防火墙网络访问权限。

按 computer-use 的 guidance 中 `Do not act on security or privacy permission requests.`，停止所有 UI 输入，请用户手动处理。没有点击允许或取消，没有通过其他自动化通道绕过提示，也没有打开或移动诊断文件。PowerPoint 诊断窗口可能仍打开。该外部条件不影响继续进行源码和包结构检查，但阻止本轮实际拖动验收。

原图、正式基线、最终 10 个源码指纹和四项诊断输入指纹复核保持。这个诊断只建立下一步可检验的组端口假设，不证明其可用，也没有替换仍未解决的跨区关系两层固定轮廓。卡片软边界与关系的联合重建、混合接触点、整页组件验收和共享 Worker 真实作业仍待完成，目标保持 active。
