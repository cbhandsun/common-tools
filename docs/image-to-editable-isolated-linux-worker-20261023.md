## 保留的失败与范围

1. v1 仅解包归档而未安装第三方依赖，在 settings 冷加载阶段以 MODULE_NOT_FOUND 停止。这是诊断环境构造缺项，不能计为生产验证成功。
2. v2 补依赖后仍从 Windows 只读挂载加载输入；settings 通过，Worker 消费探针在 60075ms 以 ETIMEDOUT / SIGTERM 停止。时限未放宽。后续改为镜像内输入的结果不反推它是旧超时的唯一原因。
3. v3 镜像内输入的三个消费者通过，但真实引擎缺少 `@common-tools/slideclone-core` 的本地工作区解析链接；目标模块实际存在于归档。v4 在独立镜像中从 20 个已绑定包清单建立内部链接，以对应 Docker 部署的工作区解析形态，随后全部回放和写入通过。

这次没有执行真实 npm 工作区 `ci`、新 OCR/VLM、真实队列作业、新 Office 渲染或共享 Worker 激活；消费者使用原确定性适配器，真实截图仍使用冻结 OCR、plan 和此前人类确认。新增本地链接只用于隔离部署形态，不授予外部源码或旧模块解析权限。结果不构成独立 npm tar 安装后的真实引擎消费验收，也不证明其内部链接会自动生成。已有完整 CI v2 的安装消费结果继续按其原六类探针范围理解。

三处外框 n4/n6/n8 的完整源证明、n107/n111/n119 的绘制归属及整卡分组、填充关系的路径编辑能力、大残差谱系和完整语义/组件门禁仍是未完成项。严格失败均保留，没有提高 baseline 或将近似拟合冒充完整像素证明。是否允许按可见边段拟合并明确标注近似外框的产品标准选择仍待用户答复。
