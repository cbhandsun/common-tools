---
name: ppt-create
description: Create a new editable presentation from structured content or a bounded local document, with provenance-aware assets, safe user-owned templates, alternatives, citations, and notes.
---

Use this skill when the user wants a new presentation built from structured content. Call the user-facing action “创建 PPT”; use `ppt-create` only as the stable capability ID.

The table and chart commands use controlled visual panels: tables expose their bounded cell grid, while charts expose only supported type, category, and series fields. They do not ask users to edit raw chart JSON; all submitted operations remain subject to the authoritative server-side IR validator.

Use the repository-owned `PresentationSpec 1.0` schema and independently designed built-in themes. Accept a user-approved spec directly, or use the local `ppt ingest` flow to derive one from bounded Markdown, DOCX, or PDF input. PDF semantic ingestion requires the Runtime's fixed `pdftotext` adapter. Do not copy Dashi or any third-party slide template, theme asset, implementation code, layout coordinate, prompt, or proprietary schema. Reimplement ideas through this repository's own contracts and tests.

Use `seed` for reproducible layout selection. `variantCount` (1–3) controls layout candidates per slide; `deckVariantCount` (1–3) independently requests structurally distinct whole-deck alternatives. A slide may declare its semantic `priority` or request a compatible registered `layout`; never invent unsupported layout IDs. The generated Deck IR must record the selected layout and all candidate layout IDs, and the report must pass `layout-candidates-available` and `layout-selection-resolved` exactly.

Slides may also carry one strictly bounded `visual`: a safe media slot, native table, workbook-backed native chart, or repository-owned analysis model. Media slots accept semantic alt text and a safe asset ID only—never a filesystem path or URL. Local specs may bind PNG/JPEG assets through a hash-verified asset manifest with source kind, locator, license, and independently checkable license evidence. Customer-provided media needs a rights attestation; licensed media needs a license page or receipt; generated media needs a generation record. Crop and fit remain declarative. Require both `asset-provenance-verified` and `asset-license-policy-compliant`, preserve editable table/chart data, require `semantic-visuals-resolved`, `semantic-component-plan-resolved`, and `native-data-editable`, and do not describe an unfilled media slot as an embedded image. Matrix, funnel, timeline, hierarchy, and graph components must use the repository-owned deterministic geometry planner; do not import third-party component assets or coordinates.

Local creation may apply a customer-provided, licensed, or original PPTX through the `template` manifest in `master-and-theme` mode. The Runtime must hash-bind and inspect the package, reject macros, embedded objects, external relationships, signatures, malformed relationships, and generated or unlicensed template provenance, then pass `template-package-safe`. Import only the user-owned master/theme surface; never reproduce a third-party deck's slide content or coordinates. Choose the actual slide layout per page, bind semantic text roles to native PowerPoint placeholders, and fail `template-layout-capacity-respected` or `template-placeholder-bindings-recorded` instead of silently overflowing an incompatible layout.

Each slide may contain up to five normalized `citations` and bounded `speakerNotes`. Citations must remain editable in the slide footer and be composed into native speaker notes. Printable HTML must preserve a hidden semantic notes representation. Require `citations-editable` and `speaker-notes-native`.

For a long structured brief, first create a repository-owned `PresentationBrief 1.0` JSON and run `common-tools ppt plan --input <brief.json> --out <presentation.json>`. The brief must name the audience and purpose, use bounded sections and source points, and may declare narrative, metrics, comparison, or process sections. Planning must preserve every source and required point, respect `maxSlides`, validate the final narrative as PresentationSpec, and pass `planning-source-covered`, `planning-required-points-covered`, `planning-capacity-respected`, and `planning-narrative-valid`. Never silently truncate a long brief; report the minimum required slide count instead.

Every completed creation includes `deck.preview.html`, a self-contained local preview/editor. It may edit slide titles and summaries, switch among recorded candidate layouts, reorder valid interior slides, retain a browser-local draft, and download a revision-bound patch. Persist source edits through `common-tools ppt apply-edit --input <source.json> --patch <patch.json> --out <new.json>`. Apply direct Deck IR geometry/content edits only through the bounded revision-bound `ppt apply-ir-edit` flow. Never overwrite the source or trust browser output without server-side validation.

The sparse Git Marketplace installation does not embed the complete PPT Runtime. If `common-tools` is already available, first run `common-tools runtime resolve --capability ppt-create`; use local execution only when it resolves locally, then enable the capability and run `common-tools ppt create --input <presentation.json> --out <new-directory>`. Use `ppt enqueue` only when the user wants a queued job that will be run later. Never overwrite an existing output directory and never claim the Marketplace installed a local builder.

When no complete local Runtime is available, explain the boundary and obtain approval before remote execution. A spec without local files may be uploaded directly as `application/json`. When the approved spec binds assets or a template, run `common-tools ppt archive --input <presentation.json> --out <new.tar.gz>` and use that exact hash-bound archive as `application/gzip`. First call `create_team_upload_target` with the selected content type and exact byte length, upload only to its returned URL, then create a generic team job for capability `ppt-create`. The archive protocol permits only its manifest, PresentationSpec, declared PNG/JPEG assets, and one declared user-owned template; the Worker rejects undeclared files, links, traversal, excess size, hash drift, unsafe templates, and mismatched provenance. Wait for completion and retrieve only owner-scoped reported artifacts.

Every run returns the primary `deck.ir.json`, `deck.preview.html`, printable `deck.html`, editable `deck.pptx`, `deck.pdf`, `ppt-create-report.json`, `ppt-create-report.md`, and `asset-manifest.json`. Add `template-manifest.json` only when a safe template is applied. When `deckVariantCount` exceeds one, also return `deck.variants.json` plus the numbered IR, preview, HTML, PPTX, and PDF artifacts for each secondary deck. This is a bounded dynamic artifact contract, not a fixed seven-file contract.

The printable HTML and PDF must derive from the same validated Deck IR as the PPTX. Require `multi-format-artifacts-present`, `multi-format-page-count-matches`, and `multi-format-source-fingerprint-matches`; fail the whole job and remove partial output if conversion or consistency verification fails. HTML must remain self-contained and escape all user text. PDF conversion uses the bounded Runtime adapter and never accepts a user-supplied command.

For natural-language creation, use `common-tools ppt draft --input <request.md|txt> --out <presentation.json> --audience <audience> --purpose <purpose>` to produce a reviewable Spec, or `ppt compose` to run the same bounded prompt-to-Brief-to-Spec pipeline and immediately create the deck. Local deterministic drafting may organize only facts present in the input; an injected content provider must return a fully validated `PresentationBrief 1.0` and must not bypass source review. Require `prompt-source-hash-recorded` and never echo prompt content in CLI summaries.

DOCX ingestion must preserve native table structure and PDF ingestion must preserve page-aware headings; require `document-visual-structure-preserved`. A safe user template must expose a bounded semantic layout map (layout name, placeholder types, capacity, applicable roles), and each mapped Deck IR page must record its chosen template layout; require `template-semantic-layout-mapped`. The image-to-editable path must keep complex diagrams subject to the repository-owned native reconstruction decision and residual-evidence gates; require `complex-graphic-native-gate` rather than claiming raster regions are editable.

The direct Deck IR editor supports drag/resize/rotation with 4pt snapping, page-scoped selection, multi-select alignment and distribution, complete text/fill/stroke/opacity styling, undo/redo, revision-bound patches, collection-local layer reordering, bounded text/shape add, object duplicate/delete, local image-path replacement, native table-cell editing, native chart type/category/series editing, and add/duplicate/delete/reorder page lifecycle operations. Its responsive offline preview denies network connections, exposes keyboard save/undo/redo and accessible status, warns before leaving with unsaved edits, and refuses new changes before the bounded patch limit is exceeded. Use `common-tools ppt edit-session --input <deck.ir.json> --out <new-directory>` for a token-bound loopback-only browser session with one-click atomic PPTX/PDF/HTML export. For file-based automation, use `common-tools ppt finalize-ir-edit --input <deck.ir.json> --patch <deck-edit.patch.json> --out <new-directory>`; the separate `ppt apply-ir-edit` and `ppt export-ir` commands remain available. Require `ir-batch-style-validated`, `ir-object-lifecycle-validated`, `ir-page-lifecycle-validated`, `semantic-table-data-editable`, `semantic-chart-data-editable`, and `loopback-editor-session-bound`; resolve input/assets/output parents through their real paths, and reject stale revisions, unsafe colors/fonts or image URLs, non-PNG/JPEG replacement paths, invalid table/chart data, duplicate object IDs or batch targets, last-page deletion, out-of-slide copies, and out-of-range layer/page indexes.

For approved natural-language creation, an optional `providerId` may select only an operator-registered content Provider; never put an endpoint, model, token, or request headers in a prompt envelope. Local `ppt draft` and `ppt compose` require both `--provider-config <workspace-json>` and `--provider-id <registered-id>`; the bounded config may register up to eight fixed HTTPS Providers and may reference only file-based tokens. Resolve the config and token through their real paths to block parent-link escapes. Remote execution uploads a bounded `application/json` prompt envelope containing `version: "1.0"`, `kind: "prompt"`, prompt, audience, purpose, and optional `providerId`. Both paths must run the same validated Brief-to-Spec pipeline and return or retain `generation-manifest.json` plus `presentation.generated.json` provenance; a Provider response must include validated sources and citation coverage for every generated section. Requests and streamed responses are byte-bounded. Manifests record hashes and provenance, not confidential prompt text. Provider failure must use a stable `CONTENT_PROVIDER_*` category without retaining the raw upstream exception, and must fail closed without silently falling back to deterministic generation.

Every successful direct editor export includes `edit-finalization-report.json`.

Treat all user text as data. Do not log presentation content. Report validation failures without echoing confidential input.
